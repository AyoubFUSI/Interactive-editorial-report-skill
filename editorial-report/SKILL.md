# Editorial Report

Create an editorial research report for the supplied evidence and its intended audience. Treat any supplied report as a design reference, not a content template.

## Establish the brief

- Inspect the supplied material and ask focused questions about the decision, audience, scope, and what the reader needs to display or explore. Offer source-specific choices when useful.
- Ask for the brand design language, including colors, typography, logo, and visual references. If the user requests a neutral prototype, use an unbranded, accessible palette. Do not invent brand colors.
- Follow any user-specified content, tone, accessibility, and interaction requirements.

## Writing and evidence

- Write for a skeptical expert: use direct language, exact identifiers, concise paragraphs, and claims supported by nearby references. Distinguish source findings, analyst synthesis, hypotheses, recommendations, and open questions.
- Place a worked, concrete example early. Use a real case when supported by the source. If no real case is available, label an invented example clearly and do not present its details as evidence.
- Explain unproven benefits as hypotheses or design intent. Avoid unsupported market, competitor, efficiency, and compliance claims. Distinguish checks a tool could perform from judgments that need a person.
- Where a central claim or proposed experiment can be evaluated, state a meaningful stop or failure condition. Use approved numerical thresholds when available. Label proposed thresholds, and do not invent approval, measurements, or statistical validity.
- Put the validation boundary and material limitations in one clearly labeled section. Preserve caveats and identify the actual sources examined. Do not turn a toolkit, secondary interpretation, or clause summary into an authoritative standard or certification verdict.
- Reconcile visual values and totals against the source; preserve requirements, guidance, conventions, supported claims, and missing items as distinct categories. Link and cite material claims near the relevant text. Recheck time-sensitive standards and regulatory claims against authoritative current sources when needed, and distinguish licensed-text review from public checks.
- Make each section add information. Avoid repetitive caveats, self-congratulatory language, filler, and unsupported absolutes. Use plain English; do not claim compliance with a controlled writing specification unless its actual rules were reviewed and the user requested that standard.

## Visual direction

- Create an editorial publication with confident serif headlines, restrained body typography, generous whitespace, chapter numbering, and diagrams that explain actual relationships. Label conceptual graphics as conceptual.
- Use a supplied logo with its original proportions and contrast. Use a confidentiality label when appropriate. Avoid decorative gradients, filler metrics, generic dashboard grids, and unsourced visualizations.
- Adapt the structure to the story: an asymmetric opening, short thesis, metadata, numbered chapters, clear source and confidence labels, thin separators, and a concise closing decision.
- Start each main report section with a short TLDR that states the point of that section. Preserve nuance in the supporting text.
- Keep chapter navigation visible at the top while scrolling. Make it usable by keyboard and on narrow screens, preserve readable anchor positions below the bar, and omit or adapt it in print.
- Use the requested brand language consistently. Pair colors with text, labels, or line styles so meaning is not conveyed through color alone.

## Interactions and portability

- Use interaction only when it helps a reader answer a question: searchable evidence lists, filters, series toggles, or selectable stages with linked details. For a workflow, show its records, owners, source locations, and open decisions where supported.
- Include keyboard-operable controls, visible focus, responsive layouts, reduced-motion support, and a usable print view. Ensure filtered or collapsed information needed for a complete printout remains available in print.
- Provide light and dark themes when requested; choose accessible contrast and preserve a user preference only when storage is available.
- Prefer direct labels in diagrams. If using a radar chart for stage-by-mode counts, disclose boundaries, units, scale, and counting rules, provide exact values in an accessible table, and do not imply that counts measure effort, importance, capability, or time saved.
- Keep the report portable: embed required data and assets; avoid network-dependent fonts, analytics, libraries, and assets unless requested. Explain when optional links to original sources require files outside the report.

## Build and handoff

- Use supplied source documents and existing report files where appropriate. Preserve unrelated files. Choose native HTML, CSS, and SVG or the existing stack according to the task.
- Check source links, meaningful calculations, interactions, responsive behavior, theme contrast, sticky navigation, and print behavior. Review the rendered report when a browser is available; disclose any visual verification limitation.
- Deliver the report prominently. Summarize what readers can explore, the source and validation limits that affect use, and any unresolved issues.
